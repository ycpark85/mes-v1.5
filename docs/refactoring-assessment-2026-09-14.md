# MES 유지보수·오류 예방 리팩토링 분석

분석일: 2026-09-14 / 대상: 개발 PC의 현재 작업 소스 / 이번 작업: 분석·재현·문서 작성만

## 판단

리팩토링을 진행할 필요가 있다. 먼저 **재현된 오류 2건과 배포 검증의 빈틈을 보완하고, 검수·재고·출고의 계산과 저장 처리를 역할별로 나누는 순서**를 권한다. 정상 동작하는 업무 규칙은 유지하면서 작은 변경마다 동일한 결과가 나오는지 검증해야 한다.

585개 Python·C#·XAML 파일을 정적 목록화했다. 그중 백엔드 실행 소스는 Python 197개, 백엔드 테스트 파일은 53개이며, 백엔드에서 100줄을 넘는 함수는 32개다. 전체 파일을 모두 같은 깊이로 감사한 것은 아니며, 검수·재고·출고·발주 완료·공통 통신·배포 검증 경로를 집중 검토했다. 파일 길이는 후보를 찾는 지표로만 사용했다.

분석 기준은 운영 배포본이 아닌 **아직 커밋되지 않은 최근 수정까지 포함한 개발 작업 소스**다. 운영 서버 및 업무 DB는 이번에 접속·조회·수정하지 않았다. 9월 9일 백업에서 발견했던 데이터 불일치가 현재 운영에도 같은 상태라고 단정하지 않는다.

사용자가 확인한 현재 동작을 리팩토링의 기준으로 고정한다.

- 신규 검수의 재고 출고·생산 출고는 0에서 직접 입력한다. 출고 자동배분은 다시 추가하지 않는다.
- 판매가능수량에서 생산 출고·폐기를 뺀 잔량은 자동으로 재고편입한다.
- 1차에서 편입한 재고는 2차의 기존재고로 사용하며, 이번 양품으로 중복 입력하지 않는다.
- 기존 실적 수정은 저장된 출고량을 유지한다. 동일 수량·메모 수정으로 기존 수불을 재생성하지 않는다.
- 분할검수도 저장 시 출고·재고를 반영한다. 기존재고 표는 LOT 번호·재고수량 두 열로 유지한다.
- 실제 수량의 LOT 계획 초과를 허용하며, 미달 최종 종료에는 사유를 요구한다. 미달량을 가짜 미검수량으로 만들지 않는다.
- 이월 표시 삭제와 과거 정산 자료의 내부 호환 처리를 구분한다. 과거 정산 연결을 확인 없이 삭제하지 않는다.

## R01. 부족종료 여부를 일반 메모에서 분리

**확인된 코드 동작과 재현 결과**

- `backend/app/services/order_line_short_close_service.py:46`은 부족종료 시 메모에 `[SHORT_CLOSE]` 문구를 붙인다.
- `backend/app/services/order_fulfillment_policy.py:31`은 메모에 그 문구가 있으면 완료 상태 재계산을 건너뛴다.
- `backend/app/services/order_line_update_service.py:106`은 완료된 발주도 메모 수정을 허용한다.
- 합성 데이터로 부족종료하여 `DONE`인 발주의 메모를 일반 문장으로 바꾼 뒤 상태를 재계산하자 `CLOSED`로 변경됐다. 출고수량은 바꾸지 않았다.

이는 메모를 수정하는 즉시 반드시 상태가 바뀐다는 뜻은 아니다. **문구가 없어진 뒤 완료 상태를 다시 계산하는 업무가 실행되면 기존 부족종료 결정이 유지되지 않을 수 있다.** 반대로 일반 메모에 해당 문자열이 포함돼도 종료 판단을 건너뛰는 구조다.

**개선 방향**

부족종료 여부·사유·결정자·결정 시각을 업무 상태로 관리하고 메모는 설명으로만 사용한다. 이미 존재하는 `OrderLinePlanHistory.is_short_close`의 의미와 실제 사용 경로를 확인하여 기존 구조를 재사용할지 결정한다. 동일 의미의 필드를 무작정 추가하지 않는다.

이 작업은 단순 함수 정리를 넘어 **상태 저장 방식과 기존 데이터 전환**이 필요한 후보다. 실제 변경 전에 매핑 근거·백업·미확정 자료 처리·롤백 계획을 별도로 정리해야 한다. 문자열만 보고 모든 기존 자료를 일괄 변환해서는 안 된다.

**완료 기준:** 메모를 수정·삭제해도 부족종료 결정 유지, 일반 메모에 문자열을 입력해도 완료 판단에 영향 없음, 기존 승인된 부족종료만 전환, 검수·출고·발주 목록의 상태 일치.

## R02. 입력 오류의 상세 내용이 사라지는 문제

`frontend-wpf/Mes.WpfClean/Mes.Wpf/Mes.Wpf/Infrastructure/Api/ApiClient.cs:316`의 공통 오류 해석은 `detail`을 문자열이라고 가정한다. 333행의 `GetString()`은 `detail`이 배열이면 예외를 발생시키고, 뒤의 처리에서 일반 상태코드 문구로 바뀐다.

실제 소스를 연결한 별도 실행 도구에 합성 HTTP 응답을 넣어 확인했다. 네트워크 요청은 하지 않았다.

| 응답 내용 | 현재 해석 결과 |
|---|---|
| `detail`이 문자열인 오류 | 상세 문구와 요청 ID 표시 |
| `detail`이 배열인 필드 검증 오류 | 상세 필드·이유가 사라지고 `PUT request failed: 422` 및 요청 ID만 표시 |

재현용 접두어는 영문이며 실제 앱은 `PUT 요청 실패`를 사용한다. 문제는 접두어 언어가 아니라 **수정해야 할 필드와 이유를 잃는 것**이다.

**개선 방향:** 문자열·배열·객체 오류 응답을 구분해서 해석하고, 오류코드·상태코드·필드별 안내·요청 ID를 공통 결과 모델에 보존한다. 사용자가 이해할 수 있는 필드 이름으로 안내한다. 서버 예외를 무조건 감추거나 원본 입력값·민감 정보를 통째로 출력하지 않는다.

일반 쓰기 요청의 시간 초과도 현재는 재시도 안내가 중심이다. 실제 저장 여부가 불명확한 경우에는 저장 결과를 확인할 경로를 마련하고, 중복 실행 방지 정책과 함께 다룬다. 이번에 중복 저장 오류 자체를 재현한 것은 아니다.

**완료 기준:** 필수값 누락·수량 범위·409 충돌·서버 오류·시간 초과별 안내 테스트, 요청 ID 유지, 성공 응답 처리 회귀 없음. 이 부분은 DB 변경 없이 먼저 개선할 수 있다.

## R03. 실행 버전과 서버 호환성 확인

과거 분할검수 오류는 사용자가 미업데이트 WPF 사용 때문이라고 확인했다. 현재는 `backend/app/api/v1/inspection_results.py:120`과 WPF 요청 DTO에서 수량규칙 버전 2를 확인한다. 다만 같은 규칙 버전 안의 빌드 차이까지 식별하지는 못한다.

- `backend/app/api/v1/endpoints/health.py:14`의 상태 확인은 `ok`, 준비 확인은 `ready` 중심이다.
- `backend/app/main.py:40`의 앱 버전은 고정된 `0.1.0`이다.
- 공통 API 클라이언트에 실행 빌드 정보를 전송하는 처리는 확인되지 않았다.
- `AppSettings.cs:13`은 Debug/Release에 따라 환경 설정을 선택한다. 사용자가 어떤 환경·실행본을 열었는지 확인하기 쉽게 하는 편이 좋다.

**개선 방향:** 로그인 또는 최초 접속 시 지원 규칙·최소 클라이언트 버전을 확인하고, 실행 WPF 버전·서버 빌드·환경을 확인할 수 있게 한다. 서버 요청 ID와 클라이언트 빌드를 함께 추적하되 사용자 업무 입력 화면에 기술 정보를 늘리지 않는다. 기존 배포 manifest와 검사 스크립트를 활용한다.

**완료 기준:** 구버전의 저장 차단, 지원 버전 정상 동작, 서버 접속 실패 안내, 환경·빌드 확인, 한 번의 오류 정보로 해당 실행본 추적 가능.

## R04. 리팩토링을 막아주는 테스트 기준 연결

기존 자동 검증이 없는 프로젝트는 아니다. `deploy/windows/Test-MesRelease.ps1`에는 소스 점검, 백엔드 테스트, Alembic 확인, WPF Release 빌드와 산출물 검사가 있다. 이를 유지하고 보완하는 것이 적절하다.

확인한 빈틈은 다음과 같다.

- `frontend-wpf/tests/InspectionRegression`의 23개 화면 로직 검사는 WPF 솔루션에 포함되지 않으며, `Test-MesRelease.ps1:141` 이후 검사 목록에도 별도 실행이 없다. WPF 빌드 성공만으로 수동 출고 규칙의 회귀를 검출할 수 없다.
- PostgreSQL 전용 동시성·마이그레이션 검사는 연결 설정이 없으면 건너뛴다. SQLite 테스트 통과를 운영 DB의 동시성 검증 완료로 해석하면 안 된다.
- 이번 실행에서 Windows 설치 검사 2건이 PowerShell 모듈 검색 환경 때문에 실패했다. 테스트 자식 프로세스에 Windows PowerShell 기본 모듈 경로를 지정하자 해당 파일의 3개 검사가 모두 통과했다. 실제 설치 코드의 변조 검증 실패로 단정하지 않는다.
- 검사·저장소 상태를 고정한 기준이 필요하다. 현재 최근 수정 코드와 테스트 일부는 아직 미커밋 상태다.

**개선 방향:** 기존 배포 검사에 WPF 회귀 실행과 PostgreSQL 필수 검사 단계를 명시하고, 전용 DB 미설정 시 필수 검증 완료로 표시되지 않게 한다. PowerShell 버전·모듈 경로 등 실행 전제를 자식 프로세스에서 명확히 한다. 이 목적만으로 새 테스트 프레임워크나 CI 서비스를 도입할 필요는 없다.

## R05. 검수 저장 서비스를 계산과 반영으로 분리

`backend/app/services/inspection_result_service.py`는 697줄이며, `upsert_inspection_result`는 241줄, `_apply_inventory_for_result`는 187줄이다. 중요한 문제는 크기보다 다음 책임이 함께 움직이는 점이다.

1. 발주·품목·LOT·스케줄 잠금과 수정 버전 검사
2. 이번 회차 수량 및 과거 정산 연결 검증
3. 실적·불량·첨부와 다음 검수 회차 처리
4. 이전 수불과의 차이 계산
5. 예약 유지·해제 및 출고 LOT 배정
6. 입출고 수불 반영, 변경 이력 및 완료 상태 갱신
7. 생산현황 갱신

**개선 방향:** 상위 함수는 전체 저장 순서와 트랜잭션을 조정하고, 하위 단계는 변경 전 상태 조회·수량 및 출고 변경분 계산·검증·수불 반영·이력 및 상태 갱신으로 나눈다. 수량 계산 결과를 먼저 검토할 수 있게 하되, 하나의 업무 저장을 여러 번 commit하는 구조로 바꾸지 않는다.

이미 있는 `inspection_quantity_policy`, `inspection_stock_service`, `inspection_settlement_service`, `order_fulfillment_policy`를 확장할지 먼저 판단한다. 모든 파일에 공통 repository나 추상 클래스를 추가하는 방식은 권하지 않는다.

현재 주요 검수·계획·출고 경로에서 발주를 먼저 잠그고 품목 재고를 잠그는 처리가 확인됐다. 이를 보존하고 교차 업무 테스트를 추가한다. 이번 분석에서 실제 교착상태가 재현된 것은 아니다.

**완료 기준:** 입력과 최종 수량뿐 아니라 기존 수불 ID·출고 LOT 연결·수정 이력·예약 잔량·다음 회차·완료 상태가 모두 이전과 동일. 저장 중 실패 시 전체 롤백, 중복 요청 및 동시 수정 검증.

## R06. 검수 화면과 비동기 실행의 책임 분리

`InspectionResultWindowViewModel.cs`는 1,246줄, 대응 XAML은 1,069줄이다. 조회·누적 계산·재고 계산·수동 입력·사진 업로드·파일 실행·저장 검증·요청 생성이 한 클래스에 있다. `_isInitializing`과 `_isRecalculatingInventoryPreview`로 속성 변경의 연쇄 실행을 막고 있다.

**개선 방향:** 순수한 수량 계산과 검증을 먼저 독립시키고, 저장 요청 생성 및 첨부 처리를 분리한다. 화면 레이아웃 분리는 수량 규칙 분리 이후에 진행한다. 사용자가 확인한 화면과 입력 순서를 동시에 바꾸지 않는다.

`Core/common/AsyncRelayCommand.cs:36` 및 제네릭 버전은 비동기 실행 중 상태 복원은 하지만 예외를 처리하는 공통 경계가 없다. `App.xaml.cs`의 예외 처리는 시작 단계 중심이다. 공통 API가 네트워크 오류를 처리하고 있으므로 모든 오류가 앱 종료로 이어진다는 뜻은 아니다. **파일 처리·계산 등에서 예상 밖 예외가 올라오는 경로**에 대한 안내·기록 방식을 정할 필요가 있다. 실제 사용자 앱 종료를 재현한 것은 아니다.

**완료 기준:** 0 출고 초기화, 양품 변경 시 직접 입력값 유지, 재고편입 자동 계산, 미달 사유, 분할 전환, 저장 중 재실행 방지, 실패 후 재입력 가능, 예상 밖 예외의 기록과 안내. 서버 검증은 최종 기준으로 유지하고 화면과 서버가 공통 수량 사례로 같은 결과를 검증한다.

## R07. 재고 조회의 반복 호출과 응답 의미 정리

확인한 세 가지 문제를 함께 정리하는 것이 좋다.

**반복 조회:** `inspection_schedule_query.py:59`의 반복문 안에서 매 LOT마다 생산 LOT ID를 별도 조회한다. 합성 DB에서 LOT 1개는 SELECT 7회, 20개는 26회였다. 이는 반복 조회가 늘어난다는 재현 근거이며 운영 응답시간 측정 결과는 아니다.

**반복 합산과 서로 다른 조회 시점:** `inspection_stock_service.py:59` 이후에는 각 LOT마다 예약·수불 목록을 다시 순회한다. WPF는 상세와 재고 LOT 목록을 따로 요청하고, 두 결과의 재고 합계가 다르면 `InspectionResultWindowViewModel.cs:1225`에서 재조회를 요구한다. 동시 재고 변경을 저장 시 차단하는 검증은 필요하지만, 화면의 기준 자료를 함께 반환하면 불필요한 불일치를 줄일 수 있다.

**ID 의미 혼용:** `inspection_schedule_query.py:64`의 `lot_id`는 생산 LOT가 있으면 생산 LOT ID, 없으면 재고 LOT ID가 된다. 현재 화면은 LOT 번호를 표시하지만, 이후 상세조회·수정 기능에서 잘못된 ID를 사용할 가능성이 있는 계약이다.

**개선 방향:** 생산 LOT 매핑 일괄 조회, 예약·수불을 LOT ID별로 한 번만 합산, 상세와 LOT 목록의 기준 정보 통합, 생산 LOT ID와 재고 LOT ID 분리. 기존 호환 계약과 예약 우선·선입선출 순서는 유지한다. 표에 새로운 열을 추가할 필요는 없다.

**완료 기준:** LOT 수가 늘어도 조회 횟수가 선형으로 증가하지 않는지 검사, 기존재고/같은 LOT 이전 회차/자기예약/다른예약/기존 실적 수정의 동일 결과, 조회 중 재고 변경 시 재조회 및 저장 안내, ID 연결 검사. 실제 SQL 실행계획과 속도는 별도 복제 DB에서 측정한다.

## R08. DB 제약은 기존 데이터 점검 후 보강

현재 `ProductInventory`와 `ProductInventoryLot`에는 필수값·관계·중복 방지가 있지만, `current_qty >= 0` 제약은 프로젝트 모델과 마이그레이션에서 확인되지 않았다. 출고 상태와 출고수량에는 이미 CHECK 제약이 있다. 따라서 DB 무결성 보호가 전혀 없다는 의미가 아니다.

**개선 방향:** 재고 잔량 음수 방지 등 서비스에서 항상 요구하는 조건을 DB의 마지막 방어선으로 보강할 수 있는지 검토한다. 전체재고·LOT 합계·수불 합계처럼 여러 행을 비교해야 하는 규칙은 단순 CHECK만으로 해결하려 하지 말고, 트랜잭션과 정합성 점검 도구를 함께 유지한다. 수불의 음수는 정상 출고 표현이므로 수불 수량에 일괄 `>= 0`을 추가하면 안 된다.

운영 DB의 실제 제약은 이번에 직접 조회하지 않았다. 기존 불일치 데이터의 정정은 별도 작업이며, 리팩토링 과정에서 자동으로 삭제·수정하지 않는다. 제약 변경은 기존 자료 검사·락 영향·백업·전환·롤백 계획을 먼저 제시한다.

## R09. 도면과 파일 저장 경로 정리

`backend/app/api/v1/drawing_revisions.py`는 729줄이며 API 라우터에 업로드·경로 처리·DB commit·실패 시 파일 정리·단일 파일 구호환 경로가 함께 있다. WPF의 `DrawingPageViewModel.cs`는 1,364줄로 도면·리비전·파일별 등록/교체 동작까지 담당한다.

현재 번들 저장 실패 시 파일을 정리하는 테스트가 존재한다. 이를 유지하면서 파일 저장·교체·보관 경로를 서비스로 옮기고, API는 입력과 응답 중심으로 정리한다. 정리 실패를 원래 오류보다 앞세우지는 않되, 실패한 파일 정리가 완전히 추적 불가능한 상태는 피한다.

실사용 중인 구호환 API는 요청 이력·클라이언트 참조를 확인한 후 폐기한다. 함수 이름에 legacy가 있다는 이유로 바로 지우지 않는다.

**완료 기준:** 업로드 제한·허용 경로·빈 파일·용량 초과·DB 실패 시 신규 파일 정리·교체 성공 후 구파일 정리·파일 종류 중복·기존 다운로드 호환성 검증. 이번에 새 파일 손실 장애를 재현한 것은 아니다.

## 완료 보고와 후속 수동 확인

이번 산출물은 본 분석 문서와 운영 문서의 연결 항목, 로컬 재현 보조자료다. **리팩토링 구현은 아직 시작하지 않았다.**

구현 후에는 개발 검증용 자료로 신규 검수 출고0 시작, 1차 재고편입 후 2차 출고, 기존 실적 수정, 미달 최종 종료, 부족종료 후 메모 수정, 입력 오류 안내, 실제 실행 버전 확인을 수동 점검한다. 운영 데이터 정정과 운영 배포는 별도 적용 범위로 남긴다.
