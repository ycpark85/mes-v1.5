## 보존한 업무 순서와 제약

1. 발주 → 품목 재고 → LOT → 검수 스케줄의 잠금 순서를 유지하고, 기존 실적 수정 시 조회 당시 버전을 확인한다.
2. 신규 검수의 재고 출고·생산 출고는 0에서 시작한다. 양품을 변경해도 사용자가 입력한 출고량은 덮어쓰지 않는다.
3. 판매가능수량에서 생산 출고와 폐기를 뺀 잔량을 재고편입한다. 음수를 0으로 숨기지 않고 저장 검증에서 차단한다.
4. 분할검수도 현재 회차를 저장할 때 정산한다. 1차 출고가 0이면 잔량은 재고가 되고, 2차에서는 기존재고 출고로 사용할 수 있다. 1차 재고를 2차 양품에 다시 합산하지 않는다.
5. 기존재고 표의 `LOT 번호 / 재고수량` 두 열을 유지한다. 자기예약·다른예약·FIFO 계산은 내부에서 기존 규칙대로 처리한다.
6. LOT 계획 초과 실적을 허용한다. 계획 미달 최종검수에는 미달 사유가 필요하고, 분할검수에는 다음 검수일과 분할 사유가 필요하다.
7. 수량 수정은 기존 기록과의 차이만 반영한다. 같은 값 재저장에서는 기존 수불·출고 연결·시각·이력을 불필요하게 다시 만들지 않는다.
8. 출고 감소는 기존 출고의 역순으로 반영하고, 출고 증가는 자기예약을 먼저 사용한 뒤 FIFO를 적용한다. 분할검수 후 남은 예약 유지와 최종검수 시 미사용 예약 해제를 보존한다.
9. 재고 부족, 다른 발주의 예약 침해, 출고목표 초과, 수불·출고 불일치 및 발행 문서의 정정 제약은 서버에서 계속 검사한다.
10. 서비스 안에서 별도 commit을 하지 않는다. 저장 중 실패하면 호출자의 트랜잭션에서 실적·출고·재고·예약·이력을 함께 되돌린다.

API 요청·응답 계약, DB 모델·마이그레이션, 검수 화면 XAML은 이번 단계에서 변경하지 않았다. 처리계획의 출고 시점, 순수 재고비축 생산의 출고목표 0 규칙도 유지한다.

## 예외 처리와 사진 작업

- 저장 중 같은 명령을 다시 실행하지 못하게 하고, 실패하면 입력값을 유지하면서 실행 상태를 복원한다. 쓰기 요청은 자동 재시도하지 않는다.
- 조회 도중 예상 밖 예외가 발생하면 저장을 차단하고 다시 조회하도록 안내한다. 정상 조회가 완료된 뒤 저장할 수 있다.
- 사진 업로드·열기를 공통 비동기 명령으로 연결했다. 다운로드 실패 시 파일을 열지 않고, 파일 작업 중 발생한 예외도 안내한다.
- `%LOCALAPPDATA%\Mes.Wpf\Logs\ui-errors.jsonl`에 UTC 시각, 오류 ID, 예외 종류, 실제 WPF 버전·빌드와 최대 8개 메서드 이름을 기록한다. 1MB를 넘으면 다음 기록 전에 이전 로그 한 파일로 교체한다.
- 예외 원문, 입력값, 사진 경로, 인증정보 및 메서드 인자는 로그에 기록하지 않는다. 기록 실패가 I/O·권한 문제인 경우에도 사용자 안내를 이어간다.
- 적용 범위는 공통 `AsyncRelayCommand`와 이번에 연결한 검수 화면 경로다. 다른 화면의 모든 비동기 이벤트를 정리한 것은 아니다.

## 수동 확인과 남은 범위

자동 검사에서는 실제 서버로 사진을 업로드하거나 사용자 업무 실적을 저장하지 않았다. 실제 창의 포커스·파일 선택창·사진 연결 프로그램·파일 기록 권한은 개발 화면에서 아래 순서로 확인해야 한다. 실행 중인 사용자 프로그램은 재시작하지 않았다.

1. 새 Debug 실행본으로 개발 환경에 로그인하고 검수실적등록을 연다. 기존재고가 두 열로 표시되고 신규 출고량이 0인지 확인한다.
2. 테스트용 LOT에서 1차 양품을 입력하고 출고 0으로 분할검수 저장한다. 2차에 1차 재고가 보이며 사용자가 입력한 재고 출고·생산 출고대로 저장되는지 확인한다.
3. 이미 저장한 최종검수의 조회·수정, LOT 초과 수량, 계획 미달 사유 입력을 확인한다.
4. 불량사진 선택·업로드·재조회·열기를 확인한다. 실패 후 입력이 유지되고 재실행할 수 있는지 확인한다.

이번 R05·R06의 코드와 자동 검증은 완료했다. 실제 화면 확인과 운영 배포는 별도다. 다음 후보 R07(재고 일괄 조회·응답 ID 의미 정리), R08(DB 제약 사전 점검), R09 이후의 파일 수명·캐시·조회 성능 작업은 이번 변경에 포함하지 않았다.
