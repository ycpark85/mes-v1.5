# 분할검수 체크 후 현재 회차 저장 오류 재검증

**후속 현장 확인:** 사용자가 오류 PC의 WPF가 업데이트되지 않아 서버와 버전이 달랐다고 확인했다. 본건 영어 오류의 직접 원인은 미업데이트 WPF와 운영 서버의 분할검수 규칙 불일치로 확정한다. 정확한 오류 PC 버전 번호와 업데이트 후 저장 성공은 별도 미확인이다. 아래는 이 확인 이전에 수행한 코드 재현·개발 수정본 검증 기록이다.

추가 운영 확인: 현재 운영1.0.0.40 대응 소스에는 분할0 배분 강제 코드가 없다. 아래 구버전 재현은 현재 운영 버전의 직접 원인을 확정한 것이 아니다. 사용자의 요청으로 운영 파일을 직접 확인한 결과와 제한은 [현재 운영 버전 분석](operating-version-analysis-2026-09-11.md)에 기록했다.

확인일: 2026-09-11 KST. 개발 수정본과 2026-09-09 18:30:01 운영 백업의 격리 복원본으로 검증했다. 이번 추가 검증에서는 운영 서버와 일반 개발 DB의 업무자료를 변경하지 않았다.

## 발생 단계와 원인 재현

사용자가 오류 발생 시점을 **‘분할검수 사용’을 체크하고 현재 회차를 저장할 때**로 확인했다. 사진의 영어 오류는 이 경로를 우선 대상으로 판단한다. 일정612의 기존 최종실적 수정·이월 문제는 별도로 확인된 결함이며, 사용자가 설명한 발생 단계를 대신하는 원인으로 제시하지 않는다.

이전 화면 커밋 `1b94e0c`에는 분할검수 선택 시 출고·재고편입·폐기를0으로 초기화하고 입력을 비활성화하며, 저장 요청에도0을 넣는 코드가 있다. 이 화면 코드를 별도 실행하여 양품432,000·불량10,456은 유지되지만 배분은 전부0이 되는 것을 확인했다.

수정 전 서버 수량정책은 분할검수도 즉시 정산하도록 요구한다. 이전 화면의0 배분을 이 정책에 넣으면 다음 문구가 정확히 재현된다.

```
result_ship_qty + stock_in_qty + discard_qty must equal current sellable qty plus prior unsettled sellable qty
```

이번 조건에서 판매가능 수량432,000·이월0에 비해 생산출고·재고편입·폐기 합계는0이다. 기존재고 출고65,000은 별도 재고에서 나가는 수량이므로 위 생산분 정산식에 더하지 않는다. LOT 계획535,000보다 현재 회차가 적다는 사실은 이 영어 오류의 직접 검증 조건이 아니다.

**구버전 화면과 즉시정산 서버 규칙의 충돌은 재현으로 확인했고, 이후 사용자가 실제 오류 PC의 미업데이트 WPF 사용을 확인했다.** 오류 PC의 정확한 실행 파일 버전·경로와 당시 요청 원문을 에이전트가 확보한 것은 아니므로, 특정 과거 커밋과 해당 실행 파일의 일치를 주장하지 않는다.

## 수정본 검증 결과

실제 WPF ViewModel의 `SaveAsync`가 만드는 요청을 테스트 API에서 수집하고 JSON으로 직렬화하여 실제 FastAPI 저장 경로에 전달했다. WPF 초기 조회는 모의 응답이며, 저장·재조회·수불·다음 회차 생성은 격리 PostgreSQL 복원본의 실제 구현이다. 실제 창 클릭과 네트워크 통신을 포함한 전체 E2E는 아니다.

사진의 양품432,000·불량10,456과 A000·불량내역 수량0을 사용했다. 불량 유형 식별자는 복원본에서 조회한 활성 A000의13이다. 이번 검증은 불량 합계와 상세내역을 강제로 일치시키는 새 규칙을 추가한 작업이 아니다.

### 화면 검증15개 통과

`frontend-wpf/tests/InspectionRegression/Program.cs`에 다음3개를 추가하여 기존12개를 포함한15개 검증이 통과했다.

1. 양품·불량 입력 후 분할 선택·현재 회차 저장 시 기존재고 출고65,000과 생산출고432,000을 요청에 유지한다.
2. 분할 선택을 해제했다가 다시 선택해도 출고 배분과 입력 가능 상태를 유지한다.
3. 분할을 먼저 선택하고 양품을 나중에 입력해도 정상 배분을 전송한다.

선택적 출력 인자로 저장 요청 JSON을 남기는 기능도 추가했다. 애플리케이션 소스는 앞선 수정본이 이 경로를 처리하므로 이번에 더 변경하지 않았다.

### 복원본 관련 시나리오5개 통과

로컬 `127.0.0.1:55439 / mes_restore_test_20260909_inspection`만 사용했고 인증은 검증용 의존성으로 제공했다.

| 시나리오 | 결과 |
|---|---|
| 이전 서버 수량정책에 구버전 분할0 배분 입력 | 사진 영어 오류와 정확히 일치 |
| 수정 서버에 배분0 요청 입력 | HTTP422, 미배분 차이432,000 안내 |
| 수량규칙 버전이 없는 구버전 요청 | HTTP409, 업데이트 안내 |
| 현재 화면의 정상 배분 요청을 예약 불일치가 남은 원본에 저장 | 수량식 검증 이후 재고 정합성 HTTP409 |
| 테스트 안에서 완료 발주818의 미사용 예약을 해제하고 분할→분할→최종 저장 | 성공, 중복 출고·중복 이월 없음 |

마지막 시나리오의 첫 회차는 수집한 WPF 요청을 그대로 사용했고, 후속 회차는 서버 검증용 요청이다.

| 단계 | 이번 양품 | 이번 기존재고 출고 | 이번 생산출고 | 누적 출고 | 저장 상태 |
|---|---:|---:|---:|---:|---|
| 첫 분할검수 | 432,000 | 65,000 | 432,000 | 497,000 | PARTIAL_DONE, 다음 일정 RECEIVED 생성 |
| 두 번째 분할검수 | 50,000 | 0 | 50,000 | 547,000 | PARTIAL_DONE, 다음 일정 RECEIVED 생성 |
| 최종검수 | 53,000 | 0 | 53,000 | 600,000 | DONE, 발주 DONE |

첫 회차 불량은10,456이며 최종 제품재고는0이다. 다음 회차에서 이미 정산된 양품이 미정산 이월로 다시 계산되지 않았고, 세 실적 모두 자신의 수량에 대한 정산 귀속을 유지했다. 첫 분할 저장 요청을 반복했을 때는 상태 검증으로 거절되고 출고497,000은 그대로였다. 동일 응답을 돌려주는 멱등 API로 바뀐 것은 아니다.

검수 시작의 ‘오늘 일정’ 규칙을 유지하며 역사적 자료를 검증하기 위해, 검수 시작 서비스의 업무 기준일만 각 일정 날짜인9월10일·11일로 주입했다. 운영 날짜나 DB 시스템 시각은 변경하지 않았다.

## 자료 보존과 남은 확인

일정593의 원본에는 완료 발주818의 대기 예약이 남아 있다. 수정본은 이 불일치를 표시하며 원본 상태의 정상 배분 요청도 재고 정합성 사유로 제한한다. 실제 화면도 재고 오류를 표시하고 저장을 막는다. **분할0 배분 수정과 과거 예약 정리는 모두 필요하다.** 정상 저장 테스트를 통과했다고 원본 자료가 이미 정리되었다고 판단하면 안 된다.

테스트의 예약 해제·실적·출고·수불은 트랜잭션 종료 시 되돌렸다. 전후11개 업무 테이블의 전체 행 해시가 일치했다. 새 정산 필드와 수정 이력, 불량 및 첨부내역도 포함했다. PostgreSQL 번호 시퀀스는 롤백되지 않지만 격리 검증 DB에만 영향을 준다.

검증 후 전용55439 인스턴스를 정상 종료했다. 기존 개발5432 DB와 개발 API는 이번 검증에서 중지하거나 변경하지 않았다.

남은 위험과 수동 확인은 다음과 같다.

- 오류 PC의 실제 실행 버전·연결 서버 및 배포 조합 확인.
- 완료 발주818의 과거 차감·출고 증빙을 근거로 예약 정정 범위 결정. 이번 임시 해제는 운영 정정의 증빙이 아니다.
- 수정본으로 실제 Windows 화면에서 분할 체크·현재 회차 저장·다음 회차 조회 확인. 운영 배포와 실제 PC 조작은 이번에 수행하지 않았다.
