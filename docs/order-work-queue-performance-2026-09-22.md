# 발주 대기목록 성능 분석 — 2026-09-22

초기 분석에서는 현재 개발 데이터의 조회 속도에 문제가 관찰되지 않았다. 다만 새 대기 분류와 전체 건수 계산에는 추가 비용이 있으며, 생산중 발주가 많이 쌓일수록 커진다. 아래 초기 분석 후 사용자의 요청에 따라 두 가지 최적화를 적용했다. 변경 내용과 전후 측정은 문서 마지막의 **후속 최적화 결과**를 참조한다. 운영 DB와 서버 배포는 변경하지 않았다.

## 측정 범위와 방법

- 이번에 변경한 발주 목록, LOT 생성 대기, 종료판단대기, 생산완료 목록과 처리 후 WPF 행 갱신을 대상으로 했다. 프로그램 전체의 성능 인증은 아니다.
- 개발 PC의 Python 3.14.6 / PostgreSQL 17.10, DB 연결 풀 5개 + 추가 허용 5개, 첫 페이지 20행 기준이다.
- DB 조회부터 응답 객체 생성·JSON 변환까지 측정했다. 실제 HTTP 인증·네트워크 왕복·서버컴퓨터 성능은 포함하지 않는다.
- 개발 DB는 읽기 전용 트랜잭션으로만 접근했다. 현재 발주 622건, LOT 647건, 검수일정 674건, 검수실적 621건, 수불 1,446건이다. 생산완료 558건, 생산중 64건이며 측정 당시 두 대기목록은 모두 0건이었다.
- 대기목록에 데이터가 있는 경우는 별도 로컬 PostgreSQL 테스트 DB의 임시 스키마에 1천/1만/5만 건을 생성하여 측정했다. 각 스키마는 측정 종료 후 제거했다.
- 일반 합성 데이터는 완료 80%, 진행 10%, 최종검수 후 부족 5%, 재고로 LOT 생성 보류 5%다. 미완료 집중 사례는 진행 50%, 부족 25%, 보류 25%로 구성했다. 최초 공통 테스트 발주 1건 때문에 실제 부족 목록은 비율 계산보다 1건 적다.
- 완료 LOT마다 검수 3회, 해당 발주마다 출고 수불 10건을 넣었다. 5만 발주 사례에는 LOT 47,500건, 검수일정 127,498건, 수불 424,990건이 있다. 품목·거래처가 단순한 조회 부하용 데이터이며 실제 모든 업무 이력의 분포를 재현한 것은 아니다.
- 첫 호출은 별도로 기록하고, 연결·캐시가 준비된 반복 측정값을 비교했다. 개발 데이터는 항목별 25회, 합성 데이터는 10회다. P50은 중앙값이다. 합성 데이터의 P95는 표본이 10개라 해당 표본의 최댓값이며 장기 지연 상한으로 해석하면 안 된다.
- 이전 구현은 Git `50654e1335e0ea6e24f64597c8853847126377c8`의 목록 조회 함수를 같은 DB와 응답 변환 환경에서 실행했다. 이전 배포 전체를 별도 서버에 띄운 비교는 아니다.

## 확인한 원인과 개선 우선순위

1. **생산완료 탭의 불필요한 대기 건수 계산을 줄이는 것이 첫 번째다.** `backend/app/api/v1/order_lines.py`의 목록 응답은 탭과 관계없이 `get_work_queue_counts()`를 호출한다. 생산완료 탭에서는 버튼이 보이지 않는다. 전부 미완료 1만 건에서 빈 생산완료 목록이 이전 3.59ms에서 현재 60.31ms로 늘었다. 전체 건수 계산만 52.45ms다. 생산중으로 돌아갈 때는 반드시 최신 건수를 조회하는 조건으로 응답 계약과 UI를 함께 정리해야 한다.

2. **종료판단 조건의 중복 계산을 줄이는 것이 두 번째다.** `backend/app/services/order_line_list_query.py`의 필터 결과 건수, 페이지 조회와 `order_line_work_queue.py`의 전역 버튼 건수에서 같은 업무 조건을 평가한다. 별도 실행계획에서 5만 건 종료판단대기의 필터 건수는 약 61ms, 페이지는 약 36ms, 전체 버튼 건수는 약 49ms였다. 각 숫자는 실행계획용 별도 호출 값이므로 표의 중앙값과 단순 합산하지 않는다. 후보 발주·최신 계획·수불 합산의 계산을 공유하는 방안을 비교 측정할 가치가 있다. 검색된 목록 건수와 검색에 무관한 버튼 전체 건수의 의미는 유지해야 한다.

3. **기존 전체 LOT 집계와 계획 이력 조회는 후순위다.** 현재 목록은 LOT 건수를 전체에서 묶어 조회하고, 현재 페이지 발주들의 계획 이력을 모두 가져온 뒤 최신 행을 선택한다. 표시 대상 발주의 LOT와 최신 이력만 읽는 방법은 데이터 축적 시 검토할 수 있다. 다만 기존부터 있던 구조이고, 이번 측정에서 계획 이력 조회 자체는 작았으므로 우선 넓은 구조 변경을 할 근거는 부족하다.

DB 실행계획에서는 LOT·검수일정·검수실적·최신 계획·수불의 기존 인덱스를 사용했다. 예를 들어 5만 건의 버튼 집계는 생산중 발주 1만 건만 읽었지만, 그 안에서 LOT 확인은 수천 번, 부족 후보 2,499건의 검수·수불·계획 확인은 각각 반복됐다. 현재 근거로는 인덱스를 추가하는 것보다 반복 평가를 줄이는 편이 우선이다. 측정 실행계획에는 디스크 임시 파일 쓰기나 JIT 컴파일이 나타나지 않았다.

데이터가 있는 페이지의 SQL 호출은 이전 4회에서 현재 5회로 늘었다. 화면 행마다 별도 SQL 요청을 보내는 구조는 아니다. 다만 한 SQL 안에서 발주별 조건 확인이 반복되므로 SQL 요청 횟수가 일정하다는 이유로 계산 비용도 일정하다고 볼 수는 없다.

출고 목표의 거래처명 정규화 SQL은 복잡하지만, 합성 데이터에서는 확정 계획이 있어 대부분의 대체 계산 경로가 실행되지 않았다. 해당 대체 경로가 많은 과거 데이터의 비용은 별도로 측정해야 하며, 이번 측정만으로 병목이라고 단정하지 않는다.

처리 후 자동갱신은 현재 페이지와 버튼 건수를 다시 조회하고, 화면에는 변경된 행만 반영하는 방식이다. 처리한 행 하나만 서버에서 가져오는 방식은 아니다. 주기적으로 계속 조회하는 타이머는 없으므로 화면을 가만히 두었을 때 이번 기능으로 반복 조회 부하가 생기지는 않는다.

## 후속 최적화 결과

사용자 확인 후 다음 두 가지를 구현했다.

1. 생산완료 목록은 대기 분류·전체 대기 건수를 계산하지 않는다. API의 `queue_counts: null`은 미계산을 뜻한다. WPF는 누락/null/빈 딕셔너리를 실제 0건과 구분하여 `미조회`로 표시하고, 매 조회 시작 시 이전 숫자를 지운다. 생산중으로 돌아갈 때 최신 결과를 조회한다. 조회 실패 시에도 과거 숫자나 0건을 최신 결과처럼 표시하지 않는다.
2. 생산중 대기 여부는 하나의 SQL 안에서 `order_work_queues` CTE에 한 번 계산하고, 검색 건수·페이지 행·검색과 무관한 전체 버튼 건수에 재사용한다. PostgreSQL의 `MATERIALIZED`는 해당 SQL 실행 동안만 유효하다. 요청 간 캐시나 DB 저장 상태를 추가하지 않는다. 완료 요청의 최신 상태·수량 재검증은 기존 그대로다.

검색 결과가 없거나 마지막 페이지를 벗어나도 전체 버튼 건수와 검색 결과 건수를 반환하도록 요약 행에 페이지를 외부 조인한다. 생산완료의 발주·출고·재고 수량과 수동완료 취소 기능은 유지한다. 스키마 변경, 새 인덱스, 의존성 추가는 없다.

5만 건에서 종료판단대기 중앙값은 약 47%, 생산완료 중앙값은 약 74% 감소했다. 데이터가 있는 페이지의 SQL 호출은 5회에서 3회, 빈 페이지는 3회에서 1회로 줄었다. 실행계획에서도 5만 건의 미완료 후보 1만 건에 대한 대기 평가가 1회임을 확인했고, 생산완료 실행계획에는 대기 평가와 검수 조회가 없다.

현재 구현의 8개 작업자/32회 동시 읽기는 일반 1만 건 P50 59.47ms / P95 117.00ms, 전부 미완료 1만 건 P50 58.10ms / P95 153.06ms였다. 일반 운영의 최대 사용자 수나 장시간 성능을 보장하는 시험은 아니다. 미완료 1만 건 단독 종료판단 조회에는 126.95ms의 지연 표본도 있었으므로 중앙값만을 최대 지연으로 해석하지 않는다.
