# 검수·재고 누적 변경 점검 결과

점검일: 2026-09-18, 개발 소스 기준. 이번 요청은 분석이므로 프로그램 소스·업무 DB·운영 배포를 변경하지 않았다. 문서와 별도 합성 데이터 재현 도구만 작성했다.

후속 상태: 사용자 승인 후 R1~R4 및 정리 항목을 수정했다. 아래 내용은 수정 전 재현 기록이며, 현재 상태와 검증 결과는 [수정 완료 기록](inspection-inventory-review-fixes-2026-09-18.md)을 참고한다.

## 판단

실행 오류를 일으킬 수 있는 화면·데이터 보존 문제 **4건을 재현**했다. 그중 불량 메모 덮어쓰기는 현재 수정 작업 전부터 있던 로직이고, 나머지 3건은 새 재고 화면의 비동기 조회 및 갱신 경계에 남은 문제다. 기존 자동 테스트가 모두 통과해도 이 추가 상황까지 안전하다는 뜻은 아니다.

삭제한 거래처 표시·검색, 재고 탭 전환, 검수 출고수량 자동 입력은 현재 실행 경로에서 발견되지 않았다. 다만 화면에서 더 이상 사용하지 않는 FIFO 미리보기 계산과 구 재고조정 API가 남아 있어 정리 대상이다. 과거 검수 정산 소유권 처리는 기존 자료의 수정에 필요하므로 같은 기준으로 삭제하면 안 된다.

이번 합성 검증에서는 제보된 기존 재고 39,500장과 1차 생산 100,000장이 같은 LOT로 합쳐 저장되는 현상, 검수 수량의 중복 정산, LOT 계획 초과 차단의 재발은 확인되지 않았다. 실제 운영 자료 전체를 검사한 결론은 아니다.

## 재현한 오류와 수정 우선순위

### R1. 저장된 불량 메모가 기본 메모로 바뀜 — 우선 수정

- 대상: `frontend-wpf/Mes.WpfClean/Mes.Wpf/Mes.Wpf/Modules/InspectionSchedules/ViewModels/InspectionResultWindowViewModel.cs:810`, `:894`; 같은 모듈 `Dtos/InspectionResultDtos.cs:372`, `Services/InspectionResultFormPolicy.cs:98`.
- 조건: 기존 검수의 불량내역에 작업자가 작성한 메모가 있고, 불량유형 조회가 성공한다.
- 재현: 저장 응답의 `OPERATOR_SAVED_NOTE`가 화면 초기화 후 `MASTER_DEFAULT_NOTE`로 바뀌며, 다음 저장 요청에도 기본 메모가 들어간다. 실제 서버 저장은 수행하지 않고 요청 생성까지 확인했다.
- 원인: 저장 메모를 먼저 읽은 뒤 불량유형의 코드·분류 표시를 보완하는 과정에서 메모도 기본값으로 덮어쓴다. 편집 모델의 `Memo`와 `DefectTypeMemo`는 같은 값을 가리킨다.
- 영향: 상세보기에서 당시 메모와 다른 내용을 표시할 수 있고, 다른 항목만 수정해 저장해도 기존 메모가 바뀔 수 있다. 기본 메모가 비어 있으면 기존 메모도 빈 값이 될 수 있다.
- 이력: Git 기준 수정 전 코드에도 동일한 대입이 있어, 이번 재고 배치 변경 때문에 새로 생긴 문제는 아니다.
- 수정 방향: 기존 실적을 읽을 때 저장된 메모를 보존하고, 기본 메모는 새 불량유형 선택 시에만 적용한다. 표시 보완은 코드·분류 정보에 한정한다.
- 완료 기준: 기존 메모가 있는 건·빈 메모인 건 모두 조회→수량 변경 없는 저장에서 원문을 보존해야 한다.

### R2. LOT 수량만 최신으로 바뀌고 합계는 이전 값 유지 — 우선 수정

- 대상: `frontend-wpf/Mes.WpfClean/Mes.Wpf/Mes.Wpf/Modules/Inventories/ViewModels/InventoryPageViewModel.cs:191`, `:250`.
- 조건: 재고현황 조회 후 다른 작업자의 출고·검수·조정으로 재고가 바뀐 상태에서 상세보기 또는 이력 재조회.
- 재현: 이력 응답이 선택 LOT의 현재 재고를 130,000으로 갱신해도 상단 품목 재고와 왼쪽 조회 합계는 139,500으로 남는다.
- 원인: 이력 조회가 선택 LOT의 수량·수정일시만 갱신한다. 품목 합계와 검색조건 전체의 LOT 합계는 LOT 목록 조회 응답에서만 갱신한다.
- 영향: 한 화면 안에 서로 다른 시점의 재고가 섞인다. 0 재고 제외로 조회한 행도 이력 갱신 후 0이 된 채 남을 수 있다. 이번 재현은 표시 불일치이며 DB 수량이 변한 것은 아니다.
- 수정 방향: 이력 조회와 재고 요약을 같은 조회 기준으로 갱신하거나, 수량 변경을 감지하면 관련 재고 목록·합계를 함께 새로 조회한다. 재조회 연결은 중복 호출·선택 초기화 없이 처리해야 한다. 현재 페이지 50개만 더해 품목 전체 합계를 만드는 방식은 사용하면 안 된다.
- 완료 기준: 다른 사용자 변경 후 이력 재조회에서도 LOT 수량·검색 합계·품목 합계·0 재고 필터가 정해진 조회 기준에 맞아야 한다.

### R3. 재조회 중 바꾼 LOT 선택이 원래 선택으로 되돌아감 — 우선 수정

- 대상: 같은 `InventoryPageViewModel.cs:177`, `:199`; `Views/InventoryPage.xaml:127`.
- 조건: LOT A를 선택한 상태로 LOT 목록을 재조회하고, 응답이 오기 전에 LOT B를 선택한다. 목록은 조회 중에도 선택할 수 있다.
- 재현: 요청 시작 시 LOT 12 → 대기 중 LOT 11 선택 → 응답 후 LOT 12로 복귀.
- 원인: 요청 시작 시 저장한 LOT 식별자를 응답 후 그대로 복원한다. 사용자의 더 최근 선택은 반영하지 않는다.
- 영향: 다음 상세보기나 재고조정의 대상이 사용자가 마지막으로 선택했던 LOT와 달라진다. 조정 창은 실제 대상 LOT를 다시 표시하지만 선택 자체가 바뀌는 문제는 남는다.
- 수정 방향: 응답 적용 직전의 최신 선택을 유지하고, 새 검색 결과에 없으면 선택을 해제한다. 선택 변경 순번도 확인하여 이전 요청이 최신 선택을 덮어쓰지 못하게 한다.
- 완료 기준: 느린 응답 상황에서 바꾼 LOT 선택을 유지하며, 검색에서 제외된 LOT만 선택을 해제해야 한다.

### R4. 이전 품목의 안내문이 새 품목에 표시됨 — 함께 수정

- 대상: 같은 `InventoryPageViewModel.cs:203`~`:204`.
- 조건: 열려 있는 LOT 이력이 있는 상태에서 목록 재조회가 이력 응답을 기다리는 동안 다른 품목으로 이동한다.
- 재현: 새 품목 2의 LOT 목록이 표시된 뒤, 이전 품목 1의 늦은 이력 응답이 끝나면 품목 1의 정합성 경고가 품목 2의 안내문을 덮어쓴다.
- 원인: 첫 목록 응답의 순번은 검사하지만, 그 뒤 `await LoadHistoryAsync(...)`에서 돌아온 후에는 순번·품목을 재검사하지 않고 상태 문구를 적용한다.
- 영향: 올바른 재고에 다른 품목의 경고가 붙거나, 현재 품목의 경고가 이전 안내로 덮일 수 있다. 이 재현에서 새 품목의 LOT 수량 자체는 유지됐다.
- 수정 방향: 비동기 작업 이후의 모든 화면 상태 반영 전에 요청 순번과 선택 품목을 다시 확인한다.
- 완료 기준: 이전 요청이 늦게 끝나더라도 현재 품목의 목록·선택·안내문·로딩 상태가 바뀌지 않아야 한다.

| 서버 FIFO 차감 | 실제 재고출고의 원본 LOT 배정과 예약 보호에 사용 | 유지 필요. 위 화면용 미리보기와 구분 |
| 구 품목 단위 재고조정 API | `POST /inventories/{product_id}/adjust`가 열려 있고 새 클라이언트는 사용하지 않음 | 구 클라이언트 사용 여부 확인 후 폐기 또는 같은 필수 검증 적용 |
| 과거 이월 정산·소유권 | `get_settlement_sources`, `settlement_carry_qty`, `settlement_owner_id` 사용 중 | 과거 미정산 자료의 정산·수정 보존용. UI 문구 삭제와 별개로 유지 필요 |
| 구 검수 재고 LOT 조회 API | `/inspection-schedules/{id}/stock-lots` 유지, 새 화면은 통합 응답 사용 | 구 클라이언트 호환 범위 확인 후 폐기 가능. 현재는 공통 재고 조회 로직으로 연결됨 |
| 품목 잔액 `balance_after` | 서버 호환 필드로 유지, 새 LOT 이력은 `lot_balance_after` 표시 | 두 값의 의미가 달라 무조건 통합·삭제하면 안 됨 |

구 재고조정 API는 사유가 없는 `ProductInventoryAdjustmentIn`을 허용하며, LOT 식별자가 없으면 서버도 사유를 필수로 검사하지 않는다. 메모리 DB에서 빈 사유로 증가 처리가 가능한 것을 확인했다. 새 LOT별 화면은 사유를 요구하므로 일반적인 새 화면 사용에서 발생하는 오류는 아니지만, 이전 클라이언트가 계속 쓰이면 새 제약을 우회하는 운영 경로가 된다. 인증·재고 쓰기 권한 검증 자체는 공통 라우터에 존재한다.

## 문서와 실제 기록 방식의 불일치

`docs/inventory-lot-tabs-2026-09-18.md`에는 생산 즉시 출고를 재고 입고·출고로 기록하지 않는다는 설명이 남아 있다. 실제 정산 코드는 생산출고량을 포함한 검수입고를 기록한 뒤 생산출고를 별도 차감한다. 이 설명은 정정 대상이다.

동일 수량 합성 자료의 2차 원장 기록은 다음과 같다.

| 원본 LOT | 기록 | 수량 |
|---|---|---:|
| 생산 LOT | 검수입고 | +300,000 |
| 기존 LOT | 기존재고 출고 | -39,500 |
| 생산 LOT | 1차 재고 출고 | -100,000 |
| 생산 LOT | 2차 생산 출고 | -160,500 |

생산 LOT의 1차 잔액 100,000을 포함하면 최종 재고는 139,500이다. 잔액 계산이 틀린 것이 아니라, 회차의 **순재고편입 139,500**과 원장의 **검수입고 300,000**이 다른 의미다. 사용자 안내와 테스트 예시를 실제 기록 방식에 맞춰 정리해야 한다. 출고가 두 줄인 것도 서로 다른 출고 원천을 구분한 결과이므로 원장을 임의로 합치거나 삭제하지 않는다.

- 운영 서버 접속·운영 자료 조회·업무 데이터 저장·배포는 수행하지 않았다. 현재 검증은 개발 소스와 합성 자료 기준이다.
- 실제 운영 동시 사용자 수, 응답 지연, 데이터 규모에 따른 부하는 측정하지 않았다.
- 이전 정산 자료의 오류나 누락 이력을 자동 수정하는 검증은 아니다. 이월 소유권·재고 원장 불일치는 별도의 자료 대조가 필요하다.
- 여러 개발 빌드 폴더와 아직 커밋되지 않은 신규 서비스·마이그레이션·테스트 파일이 있다. 배포할 때 일부 파일이나 이전 실행파일만 가져가면 버전 불일치가 재발할 수 있어, 서버·WPF·마이그레이션을 한 릴리스로 확인해야 한다.
- 화면 관련 수정은 실제 모니터 배율, 조회 권한과 쓰기 권한 계정, 작업 중 화면 이동을 포함해 수동 검증이 필요하다.

## 권장 진행 순서

1. R1 불량 메모 보존 수정과 조회→저장 회귀검증 추가.
2. R2 재고 요약 갱신 기준 정리, R3 최신 LOT 선택 보존, R4 비동기 후 상태 검증을 같은 화면 흐름에서 수정.
3. 사용하지 않는 클라이언트 FIFO 미리보기 계산을 제거하고 실제 재고 기록 설명을 정정.
4. 구 재고조정 API의 사용 여부를 확인하고 사유 필수 규칙을 통일하거나 경로를 폐기. 과거 정산 보호 로직은 별도 유지.
5. 관련 자동 검증과 PostgreSQL 배포 검증을 마친 뒤 개발 화면에서 메모 보존, 동시 재고 변경, 느린 조회 중 선택 변경을 수동 확인.

이번 분석에서 변경한 관리 문서는 본 보고서와 `docs/project-operations.md`의 보고서 연결이다. 업무 기능 수정은 다음 작업으로 남겨 두었다.
