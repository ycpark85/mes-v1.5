# 검수실적 상세보기의 회차별 재고 표시 수정 — 2026-09-14

## 문제와 변경

저장된 1차 검수의 상세보기가 현재 LOT 잔액과 실적 수정용 가용재고를 함께 표시했다. 2차 저장 후 1차를 다시 열면 소진된 기존 LOT가 사라지고, 생산 LOT에는 2차 처리 후 잔액이 나타났다. `이전 출고완료`도 전체 발주 출고에서 선택 회차만 제외해 이후 회차를 포함했다.

상세보기는 선택 회차의 재고 처리 직후를 조회한다. 등록·수정 화면과 저장 검증은 기존의 현재 재고·예약·전체 타 회차 출고 기준을 유지한다. 재고 편입이나 출고를 다시 실행하지 않으며 업무 DB와 스키마를 수정하지 않는다.

합성 재현 사례: 기존 LOT 39,500, 1차 양품 100,000 전량 재고편입, 2차 신규 양품 300,000에서 재고 출고 139,500·생산 출고 160,500.

| 상세보기 | 기존 LOT | 생산 LOT | 회차 재고편입 | 출고누계 | 출고잔량 |
|---|---:|---:|---:|---:|---:|
| 1차 저장 후 | 39,500 | 100,000 | 100,000 | 0 | 300,000 |
| 2차 저장 후 | 0 | 139,500 | 139,500 | 300,000 | 0 |

품목 합계 139,500을 생산 LOT 수량으로 대신 표시하지 않는다. 2차 저장 후에도 1차의 LOT별 재고는 유지된다.

## 조회 계약과 이력 기준

- `GET /inspection-schedules/{id}/result?view_mode=saved`: 읽기 전용 상세보기. 기존 기본값은 `edit`이며 호환용 재고 LOT API와 저장 API는 변경하지 않는다.
- 응답의 `inventory.view_mode`로 사용 목적을 확인한다. `stock_as_of`는 재고 조회 기준시각이다. 두 조회는 기존 PostgreSQL `REPEATABLE READ, READ ONLY` 세션 안에서 수행된다.
- 선택 실적의 마지막 수불 ID까지 LOT별 입출고를 합산한다. 품목별 재고 잠금으로 순서가 정해진 수불 ID를 사용하므로 서로 다른 회차의 시간이 같아도 이후 회차를 포함하지 않는다. `balance_after`는 품목 합계이므로 LOT 잔액으로 사용하지 않는다.
- 수량 정정은 추가된 차이 수불까지 반영한다. 메모만 수정해 수불이 추가되지 않으면 재고 조회 기준은 바뀌지 않는다. 상세보기는 전체 수정 이력 버전을 선택하는 화면이 아니다.
- 수불이 없는 실적은 최초 저장 시각을 기준으로 조회한다. 같은 시각의 수불이 있어 선후를 확정할 수 없으면 확인 불가를 안내한다.
- 현재 LOT 잔액과 전체 수불 합계를 대조한다. LOT 연결 누락, 합계 불일치 또는 과거 음수 잔액이 있으면 현재 재고로 대체하지 않고 안내한다. 화면에서는 불확실한 재고·출고 요약 숫자를 숨기고 해당 회차의 검수 입력값은 유지한다.
- 저장 시점의 LOT 잔액은 예약 차감 전 물리 재고다. 과거 예약량을 추정하지 않는다. 상세보기에서 FIFO 배분이나 잔여 재고편입량을 다시 계산하지 않는다.
- 화면 제목은 `출고 / 재고 요약 (저장 시점)`, 재고 항목은 `저장 후 재고`, 표는 `저장 후 LOT별 재고`다. 열은 LOT 번호·재고수량 두 개를 유지한다.
- 출고목표는 기존의 현재 확정 처리계획 규칙을 유지한다. 과거 발주·처리계획·납기 변경 내역 전체를 재현하는 기능은 이번 범위에 포함하지 않는다.

## 검증

- 수정 전: 2차 저장 후 1차 요약과 LOT 행이 바뀌는 합성 재현 테스트 실패 확인.
- 개발 업무 DB: 제보된 두 회차를 읽기 전용으로 조회해 위 기대값과 일치함을 확인. 저장·수정하지 않음.
- WPF 자동 검사: 70개 통과. 기존 저장·사진 검사와 상세보기 추가 검사 포함.
- Debug·Release 전체 빌드: 모두 성공, 경고 0·오류 0.
- 서버 전체 검사: **379개 통과, 하위 사례 49개 통과, 1개 건너뜀**. 별도 PostgreSQL에서 새 회차별 조회 검사와 기존 필수 검사 6개가 모두 통과했다.
- 건너뛴 1개는 Windows 심볼릭 링크 생성 권한이 필요한 기존 첨부파일 검사다.
- 검사 보고서: `.tmp/inspection-saved-stock-20260914/backend-tests.xml`. 테스트 데이터는 업무 DB와 분리된 `127.0.0.1:55439/mes_regression`의 임시 스키마에서 생성·정리했다.
- 검사 종료 후 전용 PostgreSQL을 중지했다. 변경 파일 공백 검사도 통과했다.

## 적용과 수동 확인

서버를 먼저 업데이트하고 새 WPF를 실행한다. 이전 서버가 저장 시점 조회를 지원하지 않으면 새 상세보기는 업데이트 안내를 표시한다. 실행 중인 사용자의 MES를 강제로 종료하거나 운영 서버에 배포하지 않았다.

1. 최신 개발 서버·Debug WPF에서 1차 상세보기를 열어 기존 LOT와 생산 LOT가 각각 표시되는지 확인한다.
2. 2차 상세보기의 출고·재고편입량을 확인하고 다시 1차를 열어 표시가 유지되는지 확인한다.
3. 별도 테스트 건에서 최종실적의 수정 화면을 열어 현재 재고를 기준으로 수동 출고 입력과 저장이 가능한지 확인한다.

실제 화면에서 업무 실적을 저장하는 수동 검사는 미실시다. 복원이 불가능한 이전 수불 자료는 명시적인 확인 불가 안내 대상이며, 이번 수정에서 업무 이력을 임의로 보정하지 않는다.

실행 중인 개발 API(`127.0.0.1:8000`)의 공개 스키마 확인은 응답을 받지 못해 완료하지 못했다. 코드·직접 조회·자동 검사 결과와 별도로, 최신 개발 서버 실행 후 실제 화면 재조회가 필요하다.
