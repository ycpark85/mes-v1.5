# 현재 운영 배포본의 분할검수 오류 분석

확인일: 2026-09-11 KST. 대상은 운영 서버 `MES-SERVER / 172.30.1.240`의 현재 배포 파일이다. 개발 컴퓨터에서 수정한 애플리케이션 코드를 이번 판단의 기준으로 사용하지 않았다.

## 결론과 앞선 설명의 정정

**후속 현장 확인으로 원인 확정:** 사용자가 오류 PC의 WPF 버전이 달랐고, 업데이트하지 않은 상태로 사용하여 분할검수 저장 오류가 발생했다고 확인했다. 따라서 본건은 **미업데이트 WPF와 운영 서버의 분할검수 수량 규칙 불일치**로 분류한다. 근거는 사용자의 현장 확인이며, 오류 PC의 정확한 버전 번호·파일 해시·실패 요청 원문을 에이전트가 수집한 것은 아니다. 업데이트 후 동일 저장의 성공 여부도 별도로 보고받지 않았다.

현재 운영 배포 버전은 **1.0.0.40**이다. 운영 서버의 대응 소스에는 **분할검수 선택 시 출고·재고편입·폐기를0으로 강제하는 코드가 없다.** 분할 선택은 미검수만0으로 바꾸고, 생산분 잔량은 재고편입으로 계산한다. 저장 직전에는 생산출고·재고편입·폐기 합계를 검사하고 화면의 배분을 그대로 요청에 넣는다.

앞선 ‘구버전 분할0 배분 + 즉시정산 서버’ 재현은 이러한 버전 불일치의 오류 발생 구조를 뒷받침한다. 운영 배포본1.0.0.40의 대응 소스에0 강제 코드가 없다는 확인과, 실제 오류 PC가 업데이트하지 않았다는 후속 현장 확인은 양립한다. 재현에 사용한 과거 커밋을 오류 PC의 정확한 실행 버전으로 간주하지 않는다.

현재 운영 코드에서 확인한 생산출고 자동 반영 누락, 재고 요약·LOT 목록의 다른 계산 기준은 별도 결함으로 남는다. WPF 버전 불일치가 확인됐다고 해당 코드 결함이나 과거 재고·예약 불일치까지 해결된 것으로 판단하지 않는다. 이번 영어 오류의 직접 대응은 오류 PC의 호환 WPF 업데이트와 같은 분할 저장 재확인이다. 이 오류를 없애기 위해 DB 수량을 바꾸거나 서버의 수량 보존 검사를 제거할 필요는 없다.

## 현재 운영 코드에 남은 결함과 원인 후보

1. **양품이 생산출고에 자동 반영되지 않음 — 코드상 확인.** 재고출고65,000이 초기값으로 있으면 초기 자동배분을 건너뛰고, 이후 양품 증가가 생산출고 증가로 연결되지 않는다. 잔량은 재고편입으로 계산된다.
2. **전체 재고는 보이지만 FIFO 목록은 비는 조건 — 코드상 확인.** 요약은 자기 발주 예약을 복원하지만 LOT 목록은 신규 검수의 자기 발주 예약을 복원하지 않는다. 이전 보고서의 과다 예약은 이 차이에 더해진 별도 데이터 문제다.9월11일의 현재 예약값을 새로 조회한 것은 아니다.
3. **조회와 저장의 이월 대상이 다름 — 코드상 확인, 이번 현재 회차와의 연결은 미확인.** 조회는 현재 일정보다 앞선 미정산 분할만 합산하지만 저장의 `_get_prior_unsettled_results`에는 날짜·회차 선후 조건이 없다. 같은 LOT에 현재 회차보다 뒤인 미정산 분할이 존재하면 화면과 서버의 정산대상이 달라질 수 있다. 그런 자료가 이번 실패 당시 존재했는지는 확인하지 못했다.
4. **기존 정산 실적의 이월 추론과 재저장 불일치 — 별도 결함.** 조회는 입고 이력에서 과거 이월을 추론하지만 저장은 미정산 자료만 사용한다. 일정612의39,500 차이는 사용자가 제공한9월10일 보고서에서 확인된 사례이며, 신규 현재 회차 저장 오류와 동일하다고 묶지 않는다.
5. **실제 PC 실행 버전 또는 조회 이후 상태 변화 — 원인 후보.** 배포 서버가1.0.0.40인 사실은 오류 PC가 같은 파일을 실행했다는 증명이 아니다. 조회 후 다른 회차 정산으로 이월이 변하는 경우도 요청·상태 이력 없이 확정할 수 없다.

현재 운영 저장 코드도 분할검수에서는 LOT 계획 미달 검사를 건너뛰며, LOT 계획 초과를 막는 상한 검사가 없다. 그러므로 해당 영어 오류를 ‘양품이 LOT 수량보다 많아서’라고 해석할 근거는 없다.
