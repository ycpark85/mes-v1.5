## 1. 권장 결론

**조회·입력·저장·수정이 같은 수량 기준을 사용하도록 수정하고, 기존 데이터는 실제 출고·재고 증빙에 따라 정리하는 방안을 권장한다.**

오늘 오류의 직접 수정 범위는 ① 자기 예약과 FIFO 표시, ② 양품 변경 시 생산 출고 자동배분, ③ 이미 정산한 이월을 포함한 실적 수정이다. 여기에 사용자가 확정한 ④ LOT 미달 사유 종료, ⑤ 순수 재고비축의 출고목표0을 함께 반영해야 같은 업무에서 다시 충돌하지 않는다.

서버 코드만 고치거나 재고 숫자만 맞추는 것으로는 완료되지 않는다. 백엔드·WPF의 호환 배포, 데이터 정리, 동일값 재저장 및 수량 변경 검증을 하나의 수정 계획으로 관리한다. 미결정 업무정책 때문에 직접 오류 수정을 모두 미루지는 않는다.

이번 설계에 적용하는 확정 사항:

- 계획 확정·검수 저장에서 출고완료·재고 차감하는 현행 시점 유지.
- LOT 계획 초과 양품·검수 허용.
- LOT 계획 미달도 실제 처리수량과 미달 사유를 기록하고 최종 종료 허용.
- 재고생산은 순수 비축: 기존재고 출고0, 생산출고0, 출고목표0.

### 3.1 H01 — 재고 요약·FIFO 목록·실제 배분 통일

현재 함수마다 다른 ‘가용재고’를 사용한다. 같은 계산 결과를 공유하도록 변경한다.

### 3.2 H02 — 양품 변경 시 출고 자동배분 복구

현재 배포본의 일반 재계산은 양품을 늘려도 생산출고를 늘리지 않고 남는 수량을 재고편입으로 계산한다. 따라서 **생산출고가0이라는 현상과 배분 전체가0이라 저장이 실패하는 현상은 구분해야 한다.** 사진처럼 모든 배분이0이 된 정확한 원인은 오류 PC 버전과 실패 요청을 확인해야 확정할 수 있다.

양품 setter에서 무조건 기존 자동배분 함수를 호출하는 한 줄 수정은 권장하지 않는다. 현재 자동 함수는 폐기를0으로 초기화하고 기존재고를 우선 선택하므로 사용자가 지정한 값이나 재고비축 계획까지 바꿀 수 있다.

권장 동작:

1. 신규 실적은 자동배분을 기본으로 시작한다.
2. 기존재고 사용량은 확정 계획과 실제 사용가능량, 남은 목표를 기준으로 설정한다.
3. 양품·불량출고 변경 시 자동모드라면 생산 출고를 다시 계산한다.
4. 자동 생산출고=`min(정산대상−명시 폐기, 남은 출고목표−기존재고 출고)`, 각 허용 범위는0 이상으로 계산한다.
5. 재고편입=`정산대상−생산출고−명시 폐기`로 계산한다.
6. 직접 지정한 출고·폐기는 수동값으로 보존한다. 불가능한 값이 되면 조용히 자르지 말고 차이를 표시한다.
7. 기존 결과 수정창은 저장된 값 그대로 열고, 자동 재배분은 명시 동작으로 제공한다.
8. 순수 재고비축은 기존재고/생산출고0, 판매가능 잔량을 재고편입한다.

저장 버튼 주변에는 이번 실제 출고량과 재고 증감 미리보기를 표시한다. 확정된 업무규칙에 따라 검수 저장에서 실제 출고가 완료되므로, 자동으로 제안된 수량도 저장 전에 확인할 수 있어야 한다.

완료 기준: 정상 재고65,000+양품432,000, 목표600,000, 폐기0인 신규 일반 혼합계획에서 재고출고65,000·생산출고432,000·재고편입0으로 제안해야 한다. 다만 실제 납품량이 다르면 사용자가 수정할 수 있어야 한다.

### 3.3 H03 — 정산 이월과 기존 결과 수정 복구

현재612:

```text
이전 회차: 19,500 + 20,000 = 39,500 (이미 이번 결과에 정산)
현재 결과의 이번 양품: 50,000
원래 정산대상: 89,500
저장 배분: 생산출고50,000 + 재고편입39,500
현재 잘못된 재검증: 89,500 ≠ 50,000
```

**권장안은 ‘이월 정산 관계를 보존하는 방식’이다.** 원래 회차, 그 물량을 정산한 결과, 정산한 수량을 연결해 저장한다. 이미 이월을 맡은 결과는 수정할 때도 그 물량을 유지하고, 다른 결과가 중복 정산할 수 없어야 한다.

신규 저장·수정 순서:

1. 스케줄·기존 실적·관련 발주/재고를 정해진 순서로 잠그고 수정 버전을 확인한다.
2. **기존 양품·불량출고·폐기·입고원장·출고배분·정산 연결을 수정 전에 읽어 보존한다.**
3. 신규 결과는 아직 정산되지 않은 앞 회차만 가져온다. 기존 결과는 원래 자신에게 귀속된 이월을 사용한다. 새로 발견된 다른 회차 이월을 조용히 추가하지 않는다.
4. `새 정산대상 = 새 이번 판매가능량 + 보존한 이월량`으로 검증한다.
5. 조회와 저장이 같은 계산 결과를 사용한다. 원본 이월 실적은 동일 LOT의 앞 회차여야 하며 중복 연결을 금지한다.
6. 수량·배분이 같으면 수불을 다시 만들지 않는다. 메모·사진 수정은 별도로 처리한다.
7. 실제 수량 수정은 차이만 계산하고 다른 발주의 재고 사용·예약·후속 문서 영향을 검증한다.
8. 전체 성공 시 정산·실적·잔액·이력·상태를 함께 반영한다. 실패 시 전부 되돌린다.

#### 왜 변경 전 값을 보존해야 하는가

기존 양품50,000을55,000으로 바꾸는 예시에서 올바른 정산대상은 `55,000+39,500=94,500`이다. 반대로 새 양품을 먼저 저장한 다음 과거입고89,500에서 빼면 이월을34,500으로 오판한다. 이 상태에서는 양품 증가5,000이 정산에 반영되지 않을 수 있다.

#### 기존 데이터의 이월 복원

현재 원장으로 계산하는 `기존입고+기존폐기−기존판매가능`은 **과거 데이터의 이월 후보를 찾는 보조 근거**로만 사용한다. 이월 원본 목록·합계·정산시각·LOT와 일치하는지를 확인한 뒤 연결을 복원한다. 복수 해석이 가능하면 자동 복구하지 않는다.

단기적으로 같은 계산함수를 조회·저장 양쪽에 쓰는 보완은 가능하지만, 이월이 누구에게 정산됐는지 계속 원장 차이로 추측하는 방식만 남기는 것은 권장하지 않는다. 스키마 변경을 포함한 연결 보존안과 기존 데이터 변환 계획을 별도로 검토한 뒤 적용해야 한다.

완료 기준:

| 규칙 전체를 한 번에 전면 재작성 | 장기 일관성 확보 가능 | 미결정 정책까지 변경, 검증 범위·운영 영향 증가 | 오늘 장애 수정 범위로는 과도함 |
| **필수 코드 수정 묶음+정산 연결 보존+검증된 데이터 정정** | 직접 원인과 확정된 새 규칙을 함께 처리 | 스키마·데이터·클라이언트 호환 검증 필요 | **권장** |

권장안의 범위는 필요한 계산·상태·정정 기능이다. 전체 프로그램 구조를 다시 만드는 리팩토링이나 새 의존성 추가는 포함하지 않는다.

## 7. 구현 작업 묶음과 적용 순서

아래는 향후 작업 계획이며 아직 실행하지 않았다. 표시 순서는 개발·검증의 의존 관계이며, 부분 패치를 준비되는 대로 운영에 배포한다는 뜻이 아니다.

| 단계 | 작업 묶음 | 산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|---|
|1| 현재값·버전·증거 고정 |593/612 및 연관 상품의 조회 결과, 오류 PC 실행 버전, 원출고 증빙 목록 | 확인된 사실/미확인 사실이 분리됨 |
|2| 실패 사례를 개발 환경에서 재현 | 합성 자료를 사용한 자동 테스트와 화면 시나리오 | 수정 전 실패·수정 후 기대값이 명확함 |
|3| API·데이터 변경 계약 설계 | 미달 사유, 정산 원본 연결, 수정 버전, 오류코드, 호환 계획 | 스키마 변경·이월 변환·롤백 계획 검토 완료 |
|4| 공통 목표·재고·정산 계산 수정 |H01/H03/H05, 상태 동기화, 수량 수정 보호 | 서버 단위·통합 검증 통과 |
|5| WPF 입력·수정·오류 표시 수정 |H02/H04, 저장값 보존, 자동/수동 배분, 미달 사유 | 실제 사용자 순서로 화면 검증 통과 |
|6| 재발 경로 보완 | 예약 수동차감·취소·별도출고·동시저장 보호 | 모든 수량 변경 진입점이 같은 핵심 제약을 지킴 |
|7| 데이터 복구안 예행 검증 | 대상별 전후표·복구 재실행 검증·불명확 건 제외 | 실물/업무 증빙과 예상 잔액이 맞음 |
|8| 조율된 운영 적용 | 영향 기능 쓰기 중지 시간, 백업, 스키마·서버·클라이언트·데이터 적용 | 호환되지 않는 구버전 입력이 섞이지 않음 |
|9| 적용 후 확인·쓰기 재개 | 실제 버전, 조회·저장·수정·재고·원장 대조 | 아래 완료 기준 충족 |

### 7.1 이번 수정에 포함할 최소 데이터 구조 검토

- **최종 미달 사유:** 별도 저장 필드와 조회/수정 계약. 분할사유에 덮어쓰지 않음.
- **이월 정산 연결:** 원실적→정산실적과 적용 수량. 같은 원실적을 다른 정산에서 중복 사용하지 못하도록 보호.
- **정정 이력:** 수량 변경 전후·사유·작업자·원거래 연결. 메모 수정 때문에 출고 원장을 다시 만들지 않음.
- **확정 목표:** 기존 계획 이력을 최대한 사용하되 현재 유효한 계획과 정책 기준을 명시. 정상 고객 목표를 임의 변경하지 않음.

정확한 테이블·컬럼명과 제약은 구현 설계에서 정한다. 기존 데이터의 의미가 불명확한 상태로 필수값을 일괄 채우거나 제약을 먼저 강제하지 않는다. 스키마를 바꾸게 되면 DB 구조 문서와 운영 문서도 함께 갱신한다.

### 7.2 긴급 중간 배포가 꼭 필요한 경우

완성된 묶음 배포가 우선이다. 지연이 큰 경우에도 **테스트를 통과한 범위만** 중간 적용한다. 조회 개선·명확한 오류 표시·무변경 저장 분리 등은 독립 검토할 수 있으나, 새 입력 규칙을 구서버에 보내거나 검증을 제거하는 우회는 하지 않는다. 이월 귀속이 모호한 결과는 안전하지 않은 수량 수정을 열지 않는다.

### 7.3 롤백 원칙

- 운영 쓰기 재개 전 실패는 준비한 백업·호환 배포 절차로 되돌린다.
- 새 미달 종료/정산 연결을 사용한 데이터가 생긴 뒤에는 이전 코드가 그 데이터를 이해하는지 먼저 확인한다.
- 쓰기 재개 후 전체 DB를 과거 백업으로 되돌리면 새 정상 거래도 사라진다. 무조건 전체 복원하지 않고 영향 기능을 멈춘 뒤 거래별 정정 또는 수정 배포를 판단한다.
- 이전 실행 파일과 스키마를 무조건 삭제하지 않는다. 변경 전후 식별값과 복구 이력을 보존한다.

## 9. 아직 남은 확인과 이번 산출물

직접 오류 수정에 필요한 미확인 사항:

- 오류 PC의 실제 실행 버전. 서버 배포1.0.0.40만 확인된 상태다.
- 593/612 각 실패 요청의 입력 수량과 상세 오류. 접근 로그의422 건수만으로 모두 같은 원인이라 할 수 없다.
- 540,000 수동 차감의 실제 목적과 고객 납품 증빙.
- 상품1160의 실물·LOT별 재고와-50,000 원조정의 귀속.
- 같은 유형이 존재하는 전체 운영 데이터 범위.

미검수의 최종 정의, 불량 상세 중복 허용, 하루 여러 회차,0수량 종료, 출고 후 정정 권한은 규칙 정리안의 미결정 항목으로 유지한다. 거래처 가산량도 이번 수정에서 임의로 바꾸지 않는다. 이 결정이 필요한 부분과 이미 확정된 직접 오류 수정을 구분해 진행한다.

이번 작업 결과:

- 추가 파일: 이 수정 계획 문서1개. 다른 문서·코드·DB·배포 설정 변경 없음.
- 작성 이유: 규칙 목록을 오늘 오류의 구체적인 수정 방법·우선순위·데이터 정리·완료 조건으로 연결.
- 수행 검증: 핵심 저장/조회/화면/모델 코드 정적 대조, 운영 보고서와 수량 비교, 문서 계산·파일 참조 확인.
- 미수행: 코드 구현·자동 테스트 실행·운영 저장/수정/출고·데이터 정리·배포. 요청 범위가 분석과 방안 도출이기 때문.
- 남은 위험과 수동 확인: 위 미확인 자료를 수정 직전에 확인하고, 데이터 정정 전후표와 배포·롤백 계획을 구체화해야 한다.
