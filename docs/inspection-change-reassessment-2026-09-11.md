# WPF 미업데이트 원인 확인 후 개발 수정 범위 재평가

2026-09-11 KST. 사용자가 실제 오류 PC의 WPF 미업데이트를 확인한 뒤, 이미 진행한 개발 수정이 여전히 필요한지와 운영 적용 시 영향을 재검토했다. 이번 검토에서 애플리케이션 코드·DB를 추가 수정하거나 기존 변경을 되돌리지 않았다.

## 판단

**이번 분할검수 영어 오류만 해결하려면 호환되는 운영 WPF로 업데이트하고 같은 저장을 확인하는 것이 우선이다. 이 오류 자체를 이유로 개발 수정 전체나 DB 마이그레이션을 운영에 적용할 필요는 없다.**

기존 개발 수정에는 따로 재현·확인한 결함과 사용자가 확정한 업무 규칙 변경이 포함되어 있다. 따라서 미업데이트 사실이 확인됐다는 이유로 모두 무효가 되지는 않는다. 반대로 이 수정 전체가 이번 장애 해결에 필요했다거나 운영 적용에 문제가 없다고 보장해서도 안 된다. 장애의 직접 조치와 이후 개선 범위를 더 명확히 구분했어야 한다.

|---|---|---|

코드를 다시 확인했으며, `inspection_quantity_policy.py`의 생산출고+재고편입+폐기=이번 판매가능+이월 등식은 제거되거나 느슨해지지 않았다. 음수 검사와 수량 차이 안내가 추가되었다. LOT 계획 초과 허용은 운영 코드에도 이미 있었으며, 이번 개발에서 새로 바뀐 종료 규칙은 계획 미달 시 사유를 기록하고 끝낼 수 있다는 점이다.

## 현재 자료에 대한 확인

- 이 작업에서 운영 코드·DB에 개발 수정본을 적용하지 않았다. 기존 작업은 개발 PC의 코드와 개발 DB에 한정되었다.
- 이번에 로컬 `127.0.0.1:5432 / mes_db`를 `REPEATABLE READ READ ONLY`로 조회했다. DB가 `transaction_read_only=on`임을 확인했다.
- `inspection_result`, `inspection_schedule`, `lot`, `order_line`, `product_inventory`, `product_inventory_lot`, `product_inventory_movement`, `shipment_line`의 전체 행 해시는 이전 운영 백업 복원 검증 결과와 모두 일치했다. **8개 비교 테이블에서 추가 업무자료 변경은 없었다.**
- 비교에서는 마이그레이션으로 추가한 `settlement_owner_id`, `settled_sellable_qty`, `shortage_reason`을 제외했다. 그러므로 DB 전체가 미변경이라고 표현하지 않는다. 개발 DB에는 새 스키마와 정산 연결이 적용되어 있다.
- 현재 개발 스키마는 `5a6b7c8d9e0f`이며 검수 수정 이력0행, 미달 사유 입력0행이다. 테스트용 실적·수불 보정이 잔류한 징후는 이번 비교 범위에서 확인되지 않았다.

## 바로 운영에 적용하면 안 되는 이유

1. **현재 운영 최신 WPF1.0.0.40도 새 서버의 수량규칙 버전2를 전송하지 않는다.** 새 서버만 배포하면 업데이트 안내로 검수 저장이 막힌다. 개발 수정본을 적용할 때는 DB·서버·새 WPF를 호환되는 조합으로 함께 관리해야 한다.
2. **새 보호 규칙이 기존 자료의 저장을 제한한다.** 9월9일 백업 검증에서는 일정593의 과다 예약 상태 신규 저장과 일정612의 재고 차이가 남은 수량 변경이 제한됐다. 정상 저장 시나리오 일부는 격리 트랜잭션 안에서만 정정 가정을 적용한 결과다. 실제 업무 자료 정리가 완료된 것은 아니다.
3. **자동으로 정산 연결을 확정하지 못한 과거 자료가 있다.** 이전 복원 검증의28개 정산 완료 실적은 연결을 확인하기 전 일반 수정이 제한되는 대상이다. 이 수치는9월9일 백업 기준이며 현재 운영 수량을 재조회한 값은 아니다.
4. **완료 상태와 수불 수정 방식도 바뀌었다.** 원장 정정은 부호 있는 차이를 추가하며, 발주 완료는 생산 LOT 상태와 출고목표를 함께 본다. 검수 저장 한 화면의 성공만으로 납품·재고 조회·관련 업무 전체의 검증을 대신할 수 없다.

## 권장 적용 범위

이번 장애는 현재 운영 서버를 유지한 상태에서 오류 PC의 호환 WPF 업데이트와 동일 분할 저장 재확인으로 처리한다. 본건 해결을 위해 과거 재고 숫자를 바꾸지 않는다.

개발 변경은 검토 후보로 보존하되 전체를 이번 장애의 긴급 수정으로 적용하지 않는다. 재고 표시·자동배분 등 독립 결함, 이월 정산·데이터 정리, 별도로 확정한 업무 규칙을 후속 개선 범위로 검토한다. 실제로 나누어 적용할 경우 서비스·DB·화면 의존성을 확인해야 하며 파일 일부만 임의로 되돌리거나 배포하지 않는다.

재발 방지 버전 검사는 현재 개발 구현을 유지할 근거가 있다. 다만 현재1.0.0.40에 해당 필드가 없다는 사실을 배포 계획과 실제 PC 업데이트 확인에 반영해야 한다. 기존 사용자 변경과 관련 없는 코드까지 전체 되돌리는 작업은 하지 않는다.

## 검증·한계와 변경 파일

이번에 실행한 것은 실제 변경 차이, 수량정책·정산 연결·마이그레이션·재고 보호·완료 규칙·버전 계약의 정적 재검토와 위 개발 DB 읽기 전용 대조다. 애플리케이션 소스를 변경하지 않아 프로그램 테스트를 재실행하지 않았다.

이전 검증 결과는 전체 백엔드341개 통과, PostgreSQL19개 통과, WPF 후속15항목 통과, 백업 복원 관련12개와 분할 저장 후속5개 시나리오의 기대 결과 일치다. 이 결과는 검증한 조건에서의 근거이며 무결점이나 즉시 운영 적용 가능성을 뜻하지 않는다. 조건과 건너뛴 검증은 [구현 결과](inspection-correction-implementation-2026-09-10.md), [백업 검증](production-backup-rehearsal-2026-09-10.md), [분할 저장 검증](partial-inspection-save-verification-2026-09-11.md)을 참조한다.

미확인 사항은 현장 WPF 업데이트 후 동일 저장 성공, 현재 운영의 데이터 정정 대상, 실제 PC 화면·납품·출력 및 운영 배포 조합이다. 자동 복원 불가 자료와 재고 차이에 대한 증빙 확인이 필요하다.

이번 변경 파일은 본 보고서와 `docs/inspection-correction-implementation-2026-09-10.md`의 재평가 연결뿐이다. 추가 코드 수정·DB 수정·되돌리기·운영 배포는 수행하지 않았다.
